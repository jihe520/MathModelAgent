# 常见失误案例库

本文件用于沉淀团队工作中的高价值踩坑经验。每个案例都遵循统一结构，以便后续持续补充。

## 数据泄漏
- 症状：训练集或验证集中的指标被未来信息、测试集信息或结果性字段混入模型。
- 常见根因：在做特征工程或时序切分前未锁定训练/测试边界；在预测前对全体数据做标准化；将未来标签或结论用于训练。
- 检查方法：审查数据切分是否按时间或分组进行；检查 scaler/编码是否在训练集 fit；检查特征是否包含未来信息。
- 修正方式：重做数据切分，确保训练、验证、测试独立；只在训练集上拟合变换器；保留真实未来测试评估。
- 如何预防：对每个预测任务明确标注“输入特征”和“目标变量”的时间边界；在结果记录中给出训练/验证/测试划分说明。

## scipy 优化约束方向写反
- 症状：求解器返回 success，但目标值、可行性或资源利用明显异常。
- 常见根因：把“x <= C”写成“x - C >= 0”或把“g(x) >= 0”写成“g(x) <= 0”；约束方向与模型解释不一致。
- 检查方法：代入几个边界点检查符号；检查约束函数是否与业务约束一致；查看优化结果是否满足资源上限和非负条件。
- 修正方式：先写清楚真实业务约束，再统一转换成 scipy 能接受的形式；对关键约束做回代验证。
- 如何预防：在代码中保留“约束说明”注释，要求每一条关键约束都做边界代入验证。

## 整数变量直接四舍五入导致不可行
- 症状：连续解看起来合理，但取整后方案失效、资源超限或需求不满足。
- 常见根因：整数变量、0-1 变量或计数变量被直接四舍五入，而没有重新检查约束、可行性和最优性。
- 检查方法：取整后逐条回代约束；检查容量、时间窗、工位数、车辆数是否仍满足；查看是否存在明显的“不可行解”被简单修正。
- 修正方式：使用整数规划或修复启发式；若必须取整，明确执行修复步骤并重新验证。
- 如何预防：在建模阶段就声明变量类型；在结果输出中保留“取整前后对比”和“修复机制说明”。

## 求解器 success 但业务约束仍违反
- 症状：求解器返回成功，但解违反最关键业务需求，例如预算、容量、工时、数量、连续性等。
- 常见根因：只看目标函数最优，而没有重新代入全部业务约束；把求解器 “success” 当作最终结论；忽略非线性约束或活跃约束判断。
- 检查方法：对每条关键约束打印值、边界、松弛量和是否活跃；单独检查业务语义而非仅数值优化状态。
- 修正方式：重新检查约束表达式、变量边界和目标系数；必要时添加修复步骤或换更适合的求解器。
- 如何预防：求解结果报告必须包含“约束核验表”，不能只保留最终目标值。

## 论文数值与代码结果不一致
- 症状：论文中给出数值与结果记录、代码输出或图表数据不一致。
- 常见根因：代码结果更新后未同步论文；文中数字来自不同版本；四舍五入方式不统一；主文中的最终结论不是从结果表提取。
- 检查方法：逐项核对论文中的关键数值、图表和结果记录；确保最终结果来自统一数据源。
- 修正方式：统一结果来源；对关键数字做版本化记录；按同一结果表进行论文撰写。
- 如何预防：建立“结果到论文”的单一来源机制，写作阶段只引用最终结果记录，不重新估算。

## 随机算法不可复现
- 症状：同样代码在不同运行中得到不同结果；模型稳定性差，难以解释。
- 常见根因：未固定随机种子；多次运行时没有记录参数；使用了随机初始化或采样策略。
- 检查方法：检查随机种子配置；记录每次运行的参数和结果；对多次独立运行结果做稳定性分析。
- 修正方式：固定随机种子；至少记录一组可复现配置；必要时输出均值、标准差与分布。
- 如何预防：在代码和结果记录中保留随机种子和运行参数；对于启发式算法强制要求复现性说明。
