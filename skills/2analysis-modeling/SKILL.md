# 赛题分析与建模设计

## 数学建模规范参考

如需领域判断，优先读取 `../_references/modeling_core_norms.md` 中的“赛题理解与子问题识别”“假设与模型建立”和“通用题型防错”小节，并根据需要参考 `../_references/model_catalog.md` 中对应模型类型的候选方法说明。该文件仅是规范知识库，不替代本阶段的分析报告结构，也不强行把固定套路写进最终结论。

## 必须产出与决策原则

在当前工作目录的 `reports/` 子目录中创建或更新：

- `reports/ANALYSIS_MODELING_REPORT.md`：记录赛题分析、题面与附件完整性核验、子问题拆解、数据与附件理解、关键歧义和假设预检，并给出最终建模路线。
- 每个子问题至少说明输入、输出、关键变量、约束、评价指标、依赖关系、数据需求与关键风险。
- 若存在多条合理建模路线，必须给出候选模型比较；若只有一条明显合理路线，也应说明为何无需额外候选。
- 需给出基线方案 / benchmark（广义概念，可为朴素方法、简单规则、历史均值、贪心解、小规模精确解等）。
- 需给出最终推荐模型、备选模型、选择理由、不选理由、关键风险和模型组合必要性说明。
- 需区分事实 / 假设 / 待验证结论，并给出关键假设与敏感性/稳健性计划。
- 需识别论文中需要外部来源支撑的重要方法、标准、领域事实和外部数据，并以简洁的 citation needs / 文献需求写入同一报告，交给 `5writing` 处理。
- 末尾需给出代码阶段交接接口：最终模型路线、输入输出要求、关键约束与验证要求。

不要在本阶段写论文正文，不要生成最终 `paper/`，不要把图表排版任务提前到这里。

- 不要求每个子问题都写完整的大型候选比较表；复杂或多路线问题写比较表，路线明显的问题可用简短说明解释为何无需额外候选。
- 仅在关键缺失、歧义或冲突会影响模型路线时触发题面/附件阶段 checkpoint。
- 在最终模型路线确定、即将进入 `3coding-visual` 前，固定触发一次用户确认 checkpoint；仅确认重大路线，不要求确认变量名、参数初始化、普通算法细节等小事项。
- CUMCM 使用 AI 时，在该重大路线 checkpoint 中保留参赛者对核心假设、模型选择和关键指标解释的确认或修改痕迹，并在 `reports/AI_USAGE_LOG.md` 更新本阶段的一条摘要；不得把 AI 建议本身当作最终模型决策依据。
- 所有新增内容继续写入 `reports/ANALYSIS_MODELING_REPORT.md`，不额外增加报告文件。

## 工作流程

### Step 0: 题面与附件完整性核验

在正式拆解子问题前，先核验题面与附件是否完整，并记录关键缺失、歧义或冲突。若这些问题会直接影响模型路线，则在本步骤触发明确 checkpoint；若不影响模型路线，则直接进入子问题拆解，不打断用户。

```markdown
## 题面与附件完整性核验

### 已知信息
...

### 关键缺失
...

### 歧义与不同解释
...

### 冲突点
...

### 结论
- 题面完整性：完整 / 部分缺失 / 存在明显冲突
- 是否影响模型路线：是 / 否
- 是否需要用户确认：是 / 否
```

### Step 1: 子问题拆解

只把题面中明确编号的顶层问题当作子问题，例如“问题一/二/三”“Problem 1/2/3”。不要把小问、背景描述、数据说明、提交要求误当成独立子问题。

在报告开头写：

```markdown
根据题目动态调整问题数量

本赛题共 X 个子问题。
```

每个子问题至少按统一结构说明：

- 输入数据与已知条件。
- 输出目标或决策结果。
- 关键变量或预测对象。
- 评价指标 / 目标函数。
- 约束条件。
- 与其他子问题的依赖关系。
- 是否需要新增派生变量、指标或数据处理步骤。
- 关键风险或不确定性。
- 需展示的图像或表格。

```markdown
### 子问题 X：<题目名称>

#### 1) 输入
...

#### 2) 输出
...

#### 3) 关键变量
...

#### 4) 约束条件
...

#### 5) 评价指标 / 目标
...

#### 6) 依赖关系
...

#### 7) 关键歧义
...

#### 8) 数据需求
...

#### 9) 初步建模判断
...
```

### Step 2: 歧义与假设预检

对关键歧义至少给出两种解释，并用简单验算或逻辑递进判断选择。不要在定模型前就忽略重要分歧；若某个假设会让后续条件没有边际效果，应回头调整解释。

```markdown
## 歧义与假设预检

- 歧义：...
- 两种解释：...
- 选择依据：...
- 敏感性/稳健性：...
```

### Step 3: 数据理解与总体建模路线

对每份附件做简要数据理解：

- 行列规模与字段解释；
- 缺失、异常、重复、单位不一致；
- 可直接用于建模的变量；
- 需要派生的指标。

然后给出总体路线：

```text
题面 -> 数据清洗(EDA) -> 子问题一模型 -> 子问题二模型 -> ... -> 结果检验 -> 论文展示
```

### Step 4: 建模报告（唯一模型决策中心）

在 `ANALYSIS_MODELING_REPORT.md` 中写出可交给代码阶段实现的完整方案。此步骤统一负责：

- 候选路线比较；
- 基线方案 / benchmark；
- 推荐模型 / 备选模型；
- 选择理由 / 不选理由；
- 模型组合必要性；
- 关键风险；
- 事实 / 假设 / 待验证结论；
- 关键假设与敏感性/稳健性计划。

同时识别后续正文的 citation needs：核心模型、算法或统计方法的方法学依据；非常规公式、指标、阈值或标准；赛题之外采用的领域背景事实；自主查阅并使用的外部数据或资料；以及其他明显来自外部知识而非题面、本队推导或本队计算的关键论断。将需求及其拟支撑内容简洁写入 `ANALYSIS_MODELING_REPORT.md`，不要求本阶段机械搜集文献或规定篇数。题面事实、本队计算结果以及本队自行构造、修改或推导的模型应如实标明来源性质，不得为凑引用强行匹配论文；本阶段已使用可靠外部来源时可一并记录，供写作阶段复核。

每个子问题至少包含：问题目标、符号与变量、模型假设、目标函数、约束、求解方法、输入输出、代码实现要点、结果校验方法。

若存在多条合理路线，应使用简洁比较表：

```markdown
### 子问题 X 的候选模型比较

| 候选方案 | 适用性 | 数据需求 | 假设合理性 | 可解释性 | 计算成本 | 可验证性 | 风险 | 结论 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 方案 A | ... | ... | ... | ... | ... | ... | ... | ... |
| 方案 B | ... | ... | ... | ... | ... | ... | ... | ... |
```

然后明确写：

```markdown
### 最终推荐模型
- 推荐模型：...
- 备选模型：...
- 选择理由：...
- 不选理由：...
- 关键风险：...
```

模型组合必须说明：

- 每个组件的独立职责；
- 组合是否必要；
- 是否可被更简单模型替代；
- 是否增加不必要复杂度和风险。

```markdown
### 基线方案 / benchmark
- 采用的基线方案：...
- 其作用：...
- 为什么不是最终模型：...
```

基线方案 / benchmark 是广义概念，可为朴素方法、简单规则、历史均值、贪心解、小规模精确解等。

```markdown
### 事实 / 假设 / 待验证结论
- 题面事实：...
- 建模假设：...
- 需数据验证：...
```

推荐结构：

```markdown
# 建模报告

## 1. 总体建模框架
## 2. 题面与附件完整性核验
## 3. 数据处理方案
## 4. 符号说明
## 5. 子问题一：<名称>
## 6. 子问题二：<名称>
## 7. 子问题三：<名称>
## 8. 基线方案 / benchmark
## 9. 候选模型比较与最终模型决策
## 10. 关键假设与敏感性计划
## 11. 事实 / 假设 / 待验证结论
## 12. 文献需求（citation needs）
## 13. 代码实现任务清单
```

如子问题数量不是 3 个，按实际题面调整章节，不要硬凑。

### Step 5: 最终模型决策接口

在报告末尾写出代码实现任务清单，并在其前附上最终模型决策接口：

```markdown
## 最终模型决策接口

| 子问题 | 最终推荐模型 | 备选模型 | 基线方案 / benchmark | 输入 | 输出 | 关键约束 | 验证要求 | 允许替换条件 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 问题一 | ... | ... | ... | ... | ... | ... | ... | ... |
| 问题二 | ... | ... | ... | ... | ... | ... | ... | ... |
```

```markdown
## 代码实现任务清单

| 任务 | 输入 | 输出 | 方法 | 校验 |
| --- | --- | --- | --- | --- |
| 问题一 | ... | ... | ... | ... |
| 问题二 | ... | ... | ... | ... |
```

关键要求：

- 代码实现前，必须确认“最终推荐模型”已写入此接口表。
- 代码阶段不得在未说明理由的情况下擅自更换最终模型路线。
- 若必须替代模型，必须记录替代理由、影响范围、是否仍符合原始目标，以及是否需要回到分析阶段修正结论。

### Step 6: checkpoint policy

仅在以下情况触发前置 checkpoint：

- 关键题意存在实质性歧义，且不同解释会导致不同建模路线；
- 关键附件或数据字段缺失，且缺失会改变模型类型或目标函数定义；
- 题面与附件冲突，且冲突会改变约束、变量或评价指标；
- 该子问题的最终推荐模型将显著改变后续求解方式、计算成本或论文论证方向；
- 用户要求限制某类建模方式，且该要求会影响最终路线。

固定 checkpoint 安排在“最终模型路线确定、即将进入 `3coding-visual` 前”。此时只确认重大路线，不要求用户确认变量名、参数初始化、普通算法细节等小事项。

若无关键缺失、歧义或冲突，直接继续进入代码阶段；代码阶段不能无审计地替换模型。

## 质量要求

- 所有结论都能回到题面或数据。
- 不编造数据字段和数值。
- 不跳过关键歧义分析。
- 模型既要有数学表达，也要能被代码实现。
- 数据不足或题面不清时，必须记录风险和替代方案。
- 每个关键子问题都必须说明最终建模路线与备选路线。
- 最终模型决策必须写明理由、风险和可替换条件。
- 最终 checkpoint 只确认重大路线，不批准普通细节修改。
